DECISION IMPROVEMENT

Suggestions before we change anything.

This page is a review board. Each suggestion lists the area, the idea, why it improves the decision, the effort, and a recommended path. Nothing here is implemented until a reviewer chooses the best path. Status starts at PROPOSED; set it to CHOSEN or REJECTED after review.

How to use this page.
Read the register, pick the highest-value suggestion per area, then decide the path (build / buy / defer). The “Recommended” column is the analyst’s default; the reviewer overrides it. Linked rows carry an official or in-repo source for manual checks.

Why these suggestions matter

Decision quality

  • Separates “we should build it” from “we can source it” — most failures here are data gaps, not ideas.
  • Forces a chosen path before code changes, so work is reviewable and reversible.
  • Mirrors the validation gates: a suggestion must clear a source-availability check before it is funded.

Review workflow

  1. Reviewer reads the register and the linked evidence for each row.
  2. For each suggestion, choose a path: Build, Buy/Partner, Defer, or Reject.
  3. Update the Status cell to CHOSEN or REJECTED.
  4. Only CHOSEN items move to the build backlog; everything else stays as a research record.
  5. Re-run tests/check_site.py after edits to confirm no link or source-row breaks.

Research and measurement, not betting advice. Suggestions are proposals, explicitly not source-verified results; each links to the evidence a reviewer should check. No strategy is approved for capital.
